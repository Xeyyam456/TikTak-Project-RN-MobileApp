# Tiktak — React Native app

React Native 0.83.10 (New Architecture), TypeScript, Android + iOS. Pinned above the 0.83.0 floor specifically — see Gotchas (FormData/Android regression).

## Stack
- React Navigation (native-stack), react-native-safe-area-context
- react-native-keyboard-controller + react-native-reanimated + react-native-worklets (keyboard handling — see Gotchas)
- react-native-gesture-handler — root `App.tsx` is wrapped in `GestureHandlerRootView`. `src/shared/components/BottomSheet.tsx` is our own drag-to-dismiss bottom sheet (Modal + core RN `Animated` + gesture-handler's `PanGestureHandler` on the handle only) — **not** `@gorhom/bottom-sheet` (tried and reverted, see Gotchas: incompatible with reanimated v4 on this RN version, sheet silently never became visible). `ProductDetailSheet` and `profile/OrderDetailSheet` both build on top of it. Windows CMake build fix in Gotchas still applies for this and any other native module with New Architecture codegen.
- react-native-image-picker (profile avatar picker, `ProfileScreen`) — resize at pick time via `maxWidth`/`maxHeight`/`quality` options, don't upload full-resolution camera photos.
- react-native-bootsplash (splash screen + app icon, brand: fruit basket logo + "TIKTAK" gradient wordmark)
- react-native-svg + react-native-svg-transformer (import `.svg` as components)
- axios + `react-native-mmkv` (API client + token persistence — see API layer below). `@react-native-async-storage/async-storage@1.22.3` is still a listed dependency but is **no longer used anywhere in `src/`** — token storage was migrated to MMKV on 2026-08-22; don't assume it's still the active storage layer.
- zustand (`src/shared/store/basket.store.ts`) — global basket state, so quantities added on one screen are visible everywhere without prop-drilling or a per-screen refetch race. `useBasketStore` holds `basket` + `fetchBasket`/`addItem`/`removeItem` (wrapping the `basket.service.ts` calls). Screens still call `fetchBasket()` on mount (not just once app-wide) since the basket can change server-side between visits, but all screens read from the same store so an add on one screen is instantly reflected if another screen re-renders. `@shopify/flash-list` grids that render basket-dependent quantities MUST pass `extraData={basket}` — FlashList is a PureComponent-style recycler and won't re-render cells on a store change that isn't part of `data` or `extraData` (bit us once: UI showed stale quantities after navigating back into a category screen even though the store had the right value). **`addItem` takes the full `Product`, not just a `productId`** (changed 2026-09-02) — `addNewItem()` inside the store needs the product's price/title/image to render an optimistic basket line for an item that isn't in the basket yet at all (the quantity-only-increment case can optimistically bump an existing line without this, but a brand-new item has nothing to optimistically render without the full object). All call sites (`CategoryProductsScreen`, `MyListsScreen`, `SearchScreen`, `BasketScreen`) pass the product, not an id.
- `@tanstack/react-query` + `@tanstack/react-query-persist-client` + `@tanstack/query-async-storage-persister` (added 2026-09-02) — `src/shared/api/queryClient.ts` (the `QueryClient`, `gcTime` fixed at 24h to match the persister's `maxAge` in `App.tsx`, otherwise an unused query drops from memory before it'd be written to disk, silently defeating persistence) + `src/shared/api/queryStorage.ts` (the MMKV-backed persister — its own **unencrypted** `tiktak-query-cache` MMKV instance, deliberately separate from `tokenStorage.ts`'s encrypted one since it only ever caches product/category/basket/order responses, never tokens, so it can be created synchronously without waiting on the Keychain read described below) + `src/shared/queries/` (per-domain hooks + `queryKeys.ts`). `queryClient.clear()` is called on logout so a different user logging in on the same device doesn't see the previous user's cached data. Basket add/remove/clear use optimistic updates (mutate the zustand store immediately, roll back on error) rather than waiting on the round trip.
- react-i18next + i18next, az/en/ru (added 2026-09-03) — see Internationalization below.
- `@notifee/react-native` (added 2026-09-03) — local order notifications, see Notifications below.
- `@maplibre/maplibre-react-native` (added 2026-09-04) — map-based address picker, see Structure below. Chosen over `react-native-maps` + Google Maps specifically because Google's Maps SDK requires a billing-enabled API key even to stay within the free tier; MapLibre + OpenFreeMap's public vector tiles (`https://tiles.openfreemap.org/styles/liberty`) need no API key at all. `expo` appears only as an **optional** peer dependency of this package (unlike expo-image below) — installing it does not pull in the Expo framework.
- `react-native-keychain` + `@sentry/react-native` (added 2026-09-01) — Keychain backs the MMKV encryption key (see `tokenStorage.ts` under API layer); Sentry is initialized in `App.tsx` with `enabled: !__DEV__` (`src/shared/config/env.ts`'s `SENTRY_DSN`), so it never fires from a dev build.

## API layer
- Backend contract is documented in `docs/api.md`, generated from the team's Postman collection (`Tiktak - E-commerce Api's - Stage 3-4 Final`). Re-derive from that collection (not from re-reading old chat) if endpoints change — the collection has known quirks (double slash in `orders/user`, `orders/admin` "stats" sharing its URL with "list") noted there.
- `src/shared/config/env.ts` — `BASE_URL = 'https://api.sarkhanrahimli.dev'` (real value, confirmed by Xeyyam). `httpClient.ts` appends `/api/tiktak` itself — don't include that suffix in `BASE_URL`.
- `src/shared/api/httpClient.ts` — single axios instance, base URL `${BASE_URL}/api/tiktak`. Request interceptor attaches `Authorization: Bearer` (from `tokenStorage`) + `Accept-Language`. Response interceptor catches 401, calls `/auth/refresh` once (de-duped via a shared in-flight promise so concurrent 401s don't fire multiple refreshes), retries the original request, and clears tokens if refresh fails. `/auth/*` requests themselves (login, signup, the refresh call) are excluded from this whole retry-and-refresh flow (checked via `originalRequest.url?.startsWith('/auth/')`) — without that guard, a wrong-password 401 on login would trigger the same "session expired" handling as a real mid-session expiry. **Fixed 2026-08-25**: on a genuine expiry (refresh fails for a non-auth request), it now also shows an error toast and calls `resetToWelcome()` (`src/navigation/navigationRef.ts` — a module-level `createNavigationContainerRef()` passed as `<NavigationContainer ref={navigationRef}>` in `App.tsx`, since `httpClient.ts` has no React tree to pull a navigation prop from) instead of leaving the user stranded on a broken authenticated screen after `clearTokens()`.
- `src/shared/api/tokenStorage.ts` — wraps `react-native-mmkv` (`createMMKV({ id: 'tiktak-storage', encryptionKey, encryptionType: 'AES-256' })`), **not** AsyncStorage anymore (migrated 2026-08-22). **Correction (2026-09-01): reads are no longer synchronous.** Since adding Keychain-backed MMKV encryption, the module can't create its MMKV instance at import time — the encryption key itself now lives in Android Keystore/iOS Keychain (`react-native-keychain`, generated once and reused via `Keychain.getGenericPassword`/`setGenericPassword`), which is only reachable async. Callers must `await initTokenStorage()` once before any other export is safe to call (`requireStorage()` throws `'tokenStorage used before initTokenStorage() resolved'` otherwise); `App.tsx` does this in a mount effect and gates all rendering (`if (!ready) return null;`) behind it, keeping the native splash screen up for that brief Keystore round-trip instead of flashing empty JS content. `getAccessToken`/`getRefreshToken`/`getRememberMe` themselves are still synchronous *MMKV* reads once `storage` exists — it's only the one-time init that's async now. This also means `RootNavigator`'s `initialRouteName` (Welcome vs Main) is decided **after** that gate, not "without a loading screen" as this doc previously said — don't reintroduce a synchronous `createMMKV()` call here without re-adding the async Keystore step. Also stores a `remember_me` boolean (see "Remember me" below). react-native-mmkv is on **v4**, which is a ground-up rewrite on Margelo's Nitro Modules architecture — the API is `createMMKV(config)` returning an `MMKV` instance, **not** `new MMKV(config)` (that class doesn't exist at runtime in v4, only as a type — `new MMKV()` throws `Cannot read property 'prototype' of undefined`, see Gotchas). Requires `react-native-nitro-modules` as a real (non-peer-only) dependency — installing `react-native-mmkv` alone fails the Gradle build with `Project with path ':react-native-nitro-modules' could not be found`.
- Two more MMKV instances exist besides `tokenStorage.ts`'s encrypted one, both deliberately **unencrypted** and synchronous (no Keystore wait) since neither holds sensitive data: `src/shared/api/settingsStorage.ts` (`tiktak-settings` — dark mode + language, survives logout since preferences shouldn't reset just because the user signed out) and `src/shared/utils/searchHistory.ts` (`tiktak-search-history` — recent search terms, capped at 10, most-recent-first, case-insensitive de-dupe). `src/shared/api/queryStorage.ts`'s `tiktak-query-cache` (TanStack Query persistence, see Stack above) is a fourth, same reasoning.
- **"Remember me"**: `LoginScreen` has a `Checkbox` ("Sessiyanı aktiv saxla"), default **unchecked**. On login, `auth.service.ts`'s `login(payload, rememberMe)` calls `setRememberMe(rememberMe)` in `tokenStorage.ts` before `setTokens(...)`. `tokenStorage.ts` also runs a guard **once at module load** (not per-render): `if (!getRememberMe()) clearTokens();`. Since backgrounding the app doesn't reload the JS module (the process stays alive), this only fires on a genuine cold start (process killed + relaunched) — exactly matches "stay logged in only until you actually close the app" semantics without needing a separate in-memory-only token path. Tokens are still briefly written to MMKV disk even when `rememberMe` is false (cleared again on the next cold start) — a deliberate simplicity tradeoff, not a bug, since this app has no elevated security requirement that would justify a dual-storage (memory-only vs persisted) split.
- Phone inputs (`LoginScreen`, `RegisterScreen`) always show a fixed `+994` prefix — `validation.ts`'s `applyAzPhonePrefix(text)` strips non-digits, strips a re-typed leading `994`, and re-prepends `+994`; wire it through `onChangeText={text => setPhone(applyAzPhonePrefix(text))}`, and initialize the field's state to `'+994'` (not `''`) so the prefix is there from first render. `validatePhone` treats a value equal to just `+994` as "empty" (not a format error).
- `src/shared/services/*.service.ts` — one file per domain (`auth`, `profile`, `product`, `basket`, `category`, `campaign`, `order`, `upload`), matching `docs/api.md`'s Client section. Admin endpoints are documented but have no service file yet — nothing in the app consumes them (no admin screens under `src/screens/private/`).
- Response shape is inconsistent across endpoints — most wrap in `{ message, data, result }`, and all of `orders/checkout|user|user/:id` return the raw object/array with no envelope. Each service function already accounts for this; don't assume a uniform envelope when adding new ones.
- **Correction (2026-08-17): `GET /basket` DOES use the `{ message, data }` envelope now**, contrary to what this doc said before — confirmed via `console.log` of the raw response while debugging a real bug where `getBasket()` was returning the envelope object typed as `Basket`, so `basket.items` was always `undefined` on fresh fetches (mutation endpoints like `addToBasket`/`removeFromBasket` already unwrapped correctly via `ApiEnvelope<Basket>`, which is why quantities showed immediately after tapping but vanished on next screen mount). Fixed in `basket.service.ts`'s `getBasket()` to unwrap via `ApiEnvelope<Basket>` like the others. If other "no envelope" endpoints listed above start behaving oddly, re-verify with a raw `console.log` rather than trusting this doc — the backend's contract apparently drifts.
- **Correction (2026-08-20): `GET /orders/user` and `GET /orders/user/:id` ALSO now use the `{ message, data }` envelope**, again contrary to what this doc says ("ENVELOPE YOXDUR"). Same drift pattern as `GET /basket` above — found via raw response logging while debugging orders not showing up in the new order-history screen despite existing on the account (`order.service.ts`'s `listOrders()`/`getOrder()` were treating `response.data` as the array/object directly). Fixed to unwrap via `ApiEnvelope<Order[]>`/`ApiEnvelope<Order>`.
- **Correction (2026-08-25): `POST /orders/checkout` ALSO now uses the `{ message, data }` envelope** — third confirmed instance of this exact drift pattern. Confirmed via a temporary `console.log` of the raw response while placing a real test order (response was `{"message":"Order created successfully","data":{...the actual Order...}}`). `order.service.ts`'s `checkout()` was typed as `Promise<Order>` and returned the raw axios `data` (the whole envelope) directly — harmless so far only because `CheckoutScreen.tsx` never consumed the return value, just awaited it before navigating to `OrderSuccess`. Fixed to unwrap via `ApiEnvelope<Order>` like the others. At this point every `orders/*` and `/basket` endpoint this project talks to has turned out to use the envelope despite `docs/api.md` saying otherwise for several of them — if a **new** endpoint is added, verify its actual shape with a raw log before trusting the docs, don't assume "no envelope" as the default anymore.
- **`UserProfile` has no `email` field at all** — not in the type, not in `GET /profile`, not accepted by `PUT /profile` (confirmed against `docs/api.md` and the live type). The Hesabım "Hesab məlumatlarım" screen's design mockup shows an E-mail field; per explicit product decision it's shown as a **disabled, fixed-placeholder field** (`AccountInfoScreen.tsx`, `PLACEHOLDER_EMAIL` constant) purely for visual fidelity — it is never sent to the backend. If the API ever adds real email support, wire that constant up to a real field + validation instead of assuming this is still a stub.
- **`Product.type` (`ProductMeasure`: `kg`/`gr`/`litre`/`ml`/`meter`/`cm`/`mm`/`piece`/`packet`/`box`) comes from the backend as a raw English enum value — never render it directly.** Found 2026-08-26: `ProductCard.tsx`'s quantity line and `OrderDetailSheet.tsx`'s order-item line both did `{quantity} {product.type}`, so adding a `piece`-measured product (e.g. a kostyum) to the basket showed "1 piece"/"2 piece" instead of "1 ədəd"/"2 ədəd". Fixed by `src/shared/utils/productMeasure.ts`'s `formatProductMeasure()` (a `Record<ProductMeasure, string>` map, same pattern as `order.ts`'s `getOrderStatusMeta`) — always wrap `product.type`/`item.product.type` in `formatProductMeasure(...)` when displaying it, don't add a new raw usage.
- `react-native-mmkv`/`react-native-nitro-modules` are native modules — after installing/changing their versions, a native rebuild (`cd android && ./gradlew.bat app:installDebug`) is required before `tokenStorage` actually works on-device; type-checking passing does not mean it's linked yet. (This line used to be about `async-storage`, which `tokenStorage.ts` no longer uses — see above.)
- **Verified working end-to-end** (2026-08-17, emulator `android_device`): `signup` and `login` both wired to `LoginScreen`/`RegisterScreen`, tested against the real backend above — signup returned "Qeydiyyat tamamlandı", login returned profile for a real account and stored tokens. `Button` component now supports a `loading` prop (spinner + double-submit guard); form-level API errors surface via a `formError` state + `getApiErrorMessage()` (`src/shared/utils/apiError.ts`), not per-field errors.

## Structure
- **Per-component folder convention (since 2026-08-22)**: most screens/components live as `ComponentName/ComponentName.tsx` + `ComponentName.styles.ts` (the `StyleSheet.create({...})` block, moved out) + `ComponentName.types.ts` (the `type ComponentNameProps = {...}`, if one exists) + `index.ts` (`export { default } from './ComponentName';`, plus re-exports of any named exports like `ProductCard`'s `COLUMNS`/`GRID_GAP`/... or `BasketSummaryBar`'s `SUMMARY_BAR_*`). External imports are unaffected (`@shared/components/ProductCard` still resolves, now via the folder's `index.ts`). Constants that feed directly into the style object (e.g. `CARD_WIDTH`, `HORIZONTAL_PADDING`) live in `.styles.ts`; constants used only in logic/JSX (e.g. `FALLBACK_IMAGE_URL`, debounce/timeout durations) stay inline in the `.tsx` — deliberately **not** further split into a `.constants.ts`, since most are single-use one-liners where separating them from their usage hurts readability rather than helping it (see Working agreements). Applied to every component/screen **except** `src/navigation/HomeStackNavigator.tsx` and `src/navigation/TabBar.tsx`, which are small enough (≤30 lines of styles) that splitting wasn't worth it — left flat on purpose, don't "finish the job" by converting them too.
- `src/screens/auth/` — Welcome, Login, Register (pre-login)
- `src/screens/protected/` — post-login screens: `home/` (HomeScreen — see the fixed-header note just below, CategoryProductsScreen, ProductDetailSheet, EmptyCategoryState, `AddressEditModal` — delivery address form, with a "Pick from map" row opening `MapAddressPicker`, see below), `basket/` (`BasketScreen.tsx`/`.styles.ts`/`index.ts` sit flat directly in `basket/`, **not** in their own `basket/BasketScreen/` subfolder — that middle folder was redundant since `basket/` only ever holds this one screen, flattened 2026-08-24; this is a deliberate exception to the per-component folder convention below, same reasoning as the `HomeStackNavigator.tsx`/`TabBar.tsx` exception — don't reintroduce a `BasketScreen/` wrapper), `checkout/` (CheckoutScreen, OrderItemsBox, OrderSuccessScreen — redirects to `Profile` → `OrderHistory` on a 3-second countdown after a successful order, also fires `notifyOrderPlaced()` once on mount, see Notifications below), `search/` (SearchScreen, debounced, plus a recent-searches list backed by `searchHistory.ts`), `profile/` (ProfileScreen, AccountInfoScreen, MyListsScreen — favorites grid, OrderHistoryScreen, OrderDetailSheet, AvatarPicker, MenuRow, `SettingsScreen` — dark mode toggle + language picker, added 2026-09-02, plus a "Storage" cache-clear action and an app-version line added 2026-09-04, `SupportScreen` — WhatsApp/Facebook/email contact rows, added 2026-09-04, see below)
- **Support screen, not a Settings subsection (added, then moved, 2026-09-04)**: `ProfileScreen`'s "Dəstək" row navigates to its own `SupportScreen` (`ProfileStackParamList`'s `Support` route) rather than expanding inline or living under `SettingsScreen` — it started as a `SettingsScreen` subsection, but was deliberately moved out after explicit user feedback that a user looking for help is unlikely to think to open "Settings" for it; version/cache-clear stayed in `SettingsScreen` since an "About" section at the bottom of Settings **is** a conventional, expected location. Contact links (`src/shared/config/env.ts`'s `SUPPORT_WHATSAPP_NUMBER`/`SUPPORT_FACEBOOK_URL`/`SUPPORT_EMAIL`) open via `Linking.openURL` — `https://wa.me/<number>` (not the `whatsapp://` scheme, so it degrades to opening in a browser if WhatsApp isn't installed instead of silently failing), the Facebook profile URL as-is, and `mailto:<email>`. `APP_VERSION` (`src/shared/config/appInfo.ts`) is read directly from `package.json`'s `version` field via a JSON import (already proven safe in this project — the i18n locale files use the same `resolveJsonModule` mechanism), not a native `DeviceInfo`-style package, so bumping the version for a release is a `package.json` edit, nothing more.
- **Theming / dark mode (added 2026-09-02, live system-follow added 2026-09-04)**: `src/theme/colors.ts` (`LIGHT_COLORS`/`DARK_COLORS`, both satisfying the `ThemeColors` type — extend both together, never just one) + `src/theme/ThemeContext.tsx` (`ThemeProvider`/`useTheme()` → `{ colors, isDark, setDarkModeEnabled }`). Per-component styling uses a `createStyles(colors)` factory called as `useMemo(() => createStyles(colors), [colors])` inside the component, replacing the old module-level static `StyleSheet.create({...})` pattern — a `.styles.ts` file that still does `export const styles = StyleSheet.create(...)` at module scope hasn't been migrated yet. Defaults to the OS `useColorScheme()` on first launch only; once the user touches the `SettingsScreen` switch it's a manual override persisted via `settingsStorage.ts` and no longer tracks system theme changes. `ThemeProvider` wraps `ErrorBoundary` in `App.tsx`, not the other way around — see the `ErrorBoundary` entry below, same reasoning.
  - **`ThemeProvider` also follows the device's OS theme *live*, not just on cold start** — a `useColorScheme()`-driven `useEffect` handles the in-foreground case, plus an `AppState('active')` listener that re-reads `Appearance.getColorScheme()` as a fallback, because on-device testing (real Xiaomi/MIUI hardware) showed the live `useColorScheme()` change event can fire for the *first* in-foreground OS theme flip in a session and then silently stop firing for a second one — the AppState listener catches what that live event misses whenever the app regains foreground. Both are inert whenever `hasDarkModeOverride()` is true (see `settingsStorage.ts`).
  - **Fixed 2026-09-04: long-press `SettingsScreen`'s switch to reset back to "follow system"** (`resetDarkModeToSystem()` in `ThemeContext.tsx`, `resetDarkModeOverride()` in `settingsStorage.ts`, wired via `ThemeSwitch`'s new optional `onLongPress` prop) — clears `tiktak_dark_mode_enabled` from MMKV and immediately re-syncs `isDark` from `Appearance.getColorScheme()`, with a success toast (`settings.darkModeReset`) since the gesture has no other visible feedback, plus a permanent hint line under the switch (`settings.darkModeResetHint`) so it's discoverable without being told. Before this fix, tapping the switch even once (including just to try it) had no way back short of clearing MMKV by hand — this had already caused two rounds of "dark mode stopped following the system, must be a bug" confusion, both traced (via a temporary `console.log` of `hasDarkModeOverride()`/`Appearance.getColorScheme()` in `ThemeProvider`) to exactly this, not a code regression. **If a "system theme not followed" report comes in again, check whether the user knows about the long-press before assuming a new bug.**
- **Internationalization (added 2026-09-03)**: `src/shared/i18n/i18n.ts` initializes `i18next`/`react-i18next` **synchronously at import time** (imported once, as a side effect, near the top of `App.tsx` — before anything else renders) so the first render already has the right language, same reasoning as the old synchronous-MMKV `initialRouteName` pattern. Language persists via `settingsStorage.ts`'s `getLanguage()`/`setLanguage()` (`'az' | 'en' | 'ru'`, default `'az'`). Locale files are split **two ways per language** — `src/shared/i18n/locales/<lang>/shared.json` (owned by `src/shared/components/*`/`utils/*`) and `.../screens.json` (owned by `src/screens/*`) — purely so two people/agents editing each half don't collide on the same file; both merge into one flat `translation` namespace via a **recursive `deepMerge()`**, not a shallow `{...a, ...b}` spread (a shallow spread let one file's `basket` key silently clobber the other's — both files legitimately have a top-level `basket` section). `intl-pluralrules` is imported before `i18n.init()` — Hermes has no built-in `Intl.PluralRules`, and skipping this polyfill doesn't break anything functionally but logs a scary pluralResolver warning banner on every launch. **Product decision: "AZN" is not translated** — kept identical across az/en/ru (ISO currency code convention), confirmed with the user rather than assumed. **Don't resize a card/container to fit a longer translation** (explicit user rule, hit with Russian button text overflowing `ProductCard`) — `Button` has an optional `textStyle` prop plus a `numberOfLines={1}` safety net specifically so the fix is always "shrink the text," never "grow the container."
- **Notifications (added 2026-09-03)**: `src/shared/utils/notifications.ts`, `@notifee/react-native` — pure local notifications, **no real backend push exists**; `notifyOrderPlaced(orderNumber)` (called once from `OrderSuccessScreen`) shows an immediate "order placed" notification and schedules a 30-second-delayed trigger notification simulating a "your order is being prepared" push, entirely client-side. Requests `POST_NOTIFICATIONS` permission (Android 13+) at point of use via `notifee.requestPermission()`; a denial is silently a no-op (not an error — the order still succeeded). `registerBackgroundNotificationHandler()` must be called in `index.js` **before** `AppRegistry.registerComponent`, not from inside `App.tsx`.
- **Map address picker (added 2026-09-04)**: `src/shared/components/MapAddressPicker/` (opened from `AddressEditModal`'s "Pick from map" row) + `src/shared/services/geocoding.service.ts`. Uses `@maplibre/maplibre-react-native` with OpenFreeMap's free `liberty` vector-tile style (no API key) — see Stack above for why this replaced `react-native-maps`/Google Maps. A fixed center pin stays visually anchored while the map pans underneath it; confirming reads the map's center coordinate and reverse-geocodes it via Nominatim (`nominatim.openstreetmap.org/reverse`, free, requires a custom `User-Agent` header per its usage policy, light/on-demand use only) into a display address. A locate-me button (`LocationManager.requestPermissions()` + `getCurrentPosition()` from maplibre, `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION` in `AndroidManifest.xml`) flies the camera to the device's real GPS position and shows it via `<UserLocation />`. **Deep linking/share was also explored this cycle (`tiktak://`) but fully reverted at the user's explicit request** ("no actual use case since there's no real link to open") — don't re-add it without being asked again; if it comes back up, note it was previously implemented and worked, just scoped out, not abandoned for a technical reason like expo-image was.
- **`HomeScreen`'s delivery-address bar and campaign carousel are fixed above the category grid, not inside it (fixed 2026-09-04)** — they used to live in the category `FlatList`'s `ListHeaderComponent`, which scrolls with the list content, so they rose up and off-screen along with the categories instead of staying pinned. They're now a separate `styles.fixedHeader` `View` sitting outside the `FlatList` entirely (only rendered when `!error`; the loading-skeleton branch also moved to a plain `View` alongside the `FlatList`, no longer inside its header) — only the category grid itself scrolls underneath. If a similar "should be pinned but scrolls with the list" bug shows up on another screen, check whether the fixed content was put in a `ListHeaderComponent` by mistake.
- `src/shared/components/` — Button, TextField, Input (see "Password masking" below), InputLabel, Checkbox (used by `LoginScreen`'s "remember me"), AppHeader (top bar with basket icon, used by HomeStackNavigator), ProductCard (grid card used by both `HomeScreen`/`CategoryProductsScreen` and `MyListsScreen`'s favorites grid — exports `COLUMNS`/`GRID_GAP`/`HORIZONTAL_PADDING` layout constants), BasketSummaryBar (floating add-to-basket summary bar, exports its own height/gap constants for screens to reserve list padding), ConfirmModal (used by `ProfileScreen` for logout confirmation and `BasketScreen`'s "Səbəti təmizlə"), ErrorState (message + "Yenidən cəhd et" retry button, used by every screen with a fetch-on-mount), AuthSwitchLink ("Hesabınız var(mı)" links shared by Welcome/Login/Register), ErrorBoundary (wraps the whole app in `App.tsx`, outermost provider — its retry remounts the whole subtree via a `key` bump on a wrapping `Fragment` rather than just clearing the error, since clearing alone re-renders the same crashed state and can loop; **don't revert to a plain `setState({error: null})`** without re-adding that reasoning), icons.tsx (inline SVG icon components — deliberately left flat, not part of the per-component folder convention above since it's a flat bag of small standalone icon functions, not one component)
- **Password masking (`Input.tsx`)**: does **not** rely on native `secureTextEntry` — see Gotchas for why (Android reveals the first typed character for ~2s). Instead always renders `•`-masked text as the controlled `value`, diffs the incoming display text against the previous mask (via common-prefix/common-suffix matching) to recover what the user actually typed/deleted, and forwards the *real* value to the parent's `onChangeText`. `secureTextEntry` is passed as `false` to the underlying `TextInput` always. The eye toggle icon follows "icon shows current state" (closed eye = masked/hidden, open eye = visible) — the opposite convention (icon shows the tap action) was tried first and reverted per explicit user preference.

- **`@gorhom/bottom-sheet` v5 silently doesn't work with this project's `react-native-reanimated` v4** — `BottomSheetModal.present()` runs with no JS error, `useEffect`/console logging confirms it's called with the correct ref and layout, but the sheet never becomes visible (tried both `enableDynamicSizing` and explicit `snapPoints`).
