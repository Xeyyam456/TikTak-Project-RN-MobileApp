# Tiktak — React Native app

React Native 0.83.10 (New Architecture), TypeScript, Android + iOS. Pinned above the 0.83.0 floor specifically — see Gotchas (FormData/Android regression).

## Stack
- React Navigation (native-stack), react-native-safe-area-context
- react-native-keyboard-controller + react-native-reanimated + react-native-worklets (keyboard handling — see Gotchas)
- react-native-gesture-handler — root `App.tsx` is wrapped in `GestureHandlerRootView`. `src/shared/components/BottomSheet.tsx` is our own drag-to-dismiss bottom sheet (Modal + core RN `Animated` + gesture-handler's `PanGestureHandler` on the handle only) — **not** `@gorhom/bottom-sheet` (tried and reverted, see Gotchas: incompatible with reanimated v4 on this RN version, sheet silently never became visible). `ProductDetailSheet` and `profile/OrderDetailSheet` both build on top of it. Windows CMake build fix in Gotchas still applies for this and any other native module with New Architecture codegen.
- react-native-image-picker (profile avatar picker, `ProfileScreen`) — resize at pick time via `maxWidth`/`maxHeight`/`quality` options, don't upload full-resolution camera photos.
- react-native-bootsplash (splash screen + app icon, brand: fruit basket logo + "TIKTAK" gradient wordmark)
- react-native-svg + react-native-svg-transformer (import `.svg` as components)
- axios + `react-native-mmkv` (API client + token persistence — see API layer below). `@react-native-async-storage/async-storage@1.22.3` is still a listed dependency but is **no longer used anywhere in `src/`** — token storage was migrated to MMKV on 2026-08-22; don't assume it's still the active storage layer.
- zustand (`src/shared/store/basket.store.ts`) — global basket state, so quantities added on one screen are visible everywhere without prop-drilling or a per-screen refetch race. `useBasketStore` holds `basket` + `fetchBasket`/`addItem`/`removeItem` (wrapping the `basket.service.ts` calls). Screens still call `fetchBasket()` on mount (not just once app-wide) since the basket can change server-side between visits, but all screens read from the same store so an add on one screen is instantly reflected if another screen re-renders. `@shopify/flash-list` grids that render basket-dependent quantities MUST pass `extraData={basket}` — FlashList is a PureComponent-style recycler and won't re-render cells on a store change that isn't part of `data` or `extraData` (bit us once: UI showed stale quantities after navigating back into a category screen even though the store had the right value).

## API layer
- Backend contract is documented in `docs/api.md`, generated from the team's Postman collection (`Tiktak - E-commerce Api's - Stage 3-4 Final`). Re-derive from that collection (not from re-reading old chat) if endpoints change — the collection has known quirks (double slash in `orders/user`, `orders/admin` "stats" sharing its URL with "list") noted there.
- `src/shared/config/env.ts` — `BASE_URL = 'https://api.sarkhanrahimli.dev'` (real value, confirmed by Xeyyam). `httpClient.ts` appends `/api/tiktak` itself — don't include that suffix in `BASE_URL`.
- `src/shared/api/httpClient.ts` — single axios instance, base URL `${BASE_URL}/api/tiktak`. Request interceptor attaches `Authorization: Bearer` (from `tokenStorage`) + `Accept-Language`. Response interceptor catches 401, calls `/auth/refresh` once (de-duped via a shared in-flight promise so concurrent 401s don't fire multiple refreshes), retries the original request, and clears tokens if refresh fails. `/auth/*` requests themselves (login, signup, the refresh call) are excluded from this whole retry-and-refresh flow (checked via `originalRequest.url?.startsWith('/auth/')`) — without that guard, a wrong-password 401 on login would trigger the same "session expired" handling as a real mid-session expiry. **Fixed 2026-08-25**: on a genuine expiry (refresh fails for a non-auth request), it now also shows an error toast and calls `resetToWelcome()` (`src/navigation/navigationRef.ts` — a module-level `createNavigationContainerRef()` passed as `<NavigationContainer ref={navigationRef}>` in `App.tsx`, since `httpClient.ts` has no React tree to pull a navigation prop from) instead of leaving the user stranded on a broken authenticated screen after `clearTokens()`.
- `src/shared/api/tokenStorage.ts` — wraps `react-native-mmkv` (`createMMKV({ id: 'tiktak-storage' })`), **not** AsyncStorage anymore (migrated 2026-08-22). `getAccessToken`/`getRefreshToken`/`getRememberMe` are **synchronous** (MMKV reads don't need `await` — existing `await getAccessToken()` call sites still work fine since `await` on a non-Promise is a no-op, wasn't worth touching every call site). This sync-ness is what lets `RootNavigator` decide its `initialRouteName` (Welcome vs Main) without a loading screen — see Structure below. Also stores a `remember_me` boolean (see "Remember me" below). react-native-mmkv is on **v4**, which is a ground-up rewrite on Margelo's Nitro Modules architecture — the API is `createMMKV(config)` returning an `MMKV` instance, **not** `new MMKV(config)` (that class doesn't exist at runtime in v4, only as a type — `new MMKV()` throws `Cannot read property 'prototype' of undefined`, see Gotchas). Requires `react-native-nitro-modules` as a real (non-peer-only) dependency — installing `react-native-mmkv` alone fails the Gradle build with `Project with path ':react-native-nitro-modules' could not be found`.
- **"Remember me"**: `LoginScreen` has a `Checkbox` ("Sessiyanı aktiv saxla"), default **unchecked**. On login, `auth.service.ts`'s `login(payload, rememberMe)` calls `setRememberMe(rememberMe)` in `tokenStorage.ts` before `setTokens(...)`. `tokenStorage.ts` also runs a guard **once at module load** (not per-render): `if (!getRememberMe()) clearTokens();`. Since backgrounding the app doesn't reload the JS module (the process stays alive), this only fires on a genuine cold start (process killed + relaunched) — exactly matches "stay logged in only until you actually close the app" semantics without needing a separate in-memory-only token path. Tokens are still briefly written to MMKV disk even when `rememberMe` is false (cleared again on the next cold start) — a deliberate simplicity tradeoff, not a bug, since this app has no elevated security requirement that would justify a dual-storage (memory-only vs persisted) split.
- Phone inputs (`LoginScreen`, `RegisterScreen`) always show a fixed `+994` prefix — `validation.ts`'s `applyAzPhonePrefix(text)` strips non-digits, strips a re-typed leading `994`, and re-prepends `+994`; wire it through `onChangeText={text => setPhone(applyAzPhonePrefix(text))}`, and initialize the field's state to `'+994'` (not `''`) so the prefix is there from first render. `validatePhone` treats a value equal to just `+994` as "empty" (not a format error).
- `src/shared/services/*.service.ts` — one file per domain (`auth`, `profile`, `product`, `basket`, `category`, `campaign`, `order`, `upload`), matching `docs/api.md`'s Client section. Admin endpoints are documented but have no service file yet — nothing in the app consumes them (no admin screens under `src/screens/private/`).
- Response shape is inconsistent across endpoints — most wrap in `{ message, data, result }`, and all of `orders/checkout|user|user/:id` return the raw object/array with no envelope. Each service function already accounts for this; don't assume a uniform envelope when adding new ones.
- **Correction (2026-08-17): `GET /basket` DOES use the `{ message, data }` envelope now**, contrary to what this doc said before — confirmed via `console.log` of the raw response while debugging a real bug where `getBasket()` was returning the envelope object typed as `Basket`, so `basket.items` was always `undefined` on fresh fetches (mutation endpoints like `addToBasket`/`removeFromBasket` already unwrapped correctly via `ApiEnvelope<Basket>`, which is why quantities showed immediately after tapping but vanished on next screen mount). Fixed in `basket.service.ts`'s `getBasket()` to unwrap via `ApiEnvelope<Basket>` like the others. If other "no envelope" endpoints listed above start behaving oddly, re-verify with a raw `console.log` rather than trusting this doc — the backend's contract apparently drifts.
- **Correction (2026-08-20): `GET /orders/user` and `GET /orders/user/:id` ALSO now use the `{ message, data }` envelope**, again contrary to what this doc says ("ENVELOPE YOXDUR"). Same drift pattern as `GET /basket` above — found via raw response logging while debugging orders not showing up in the new order-history screen despite existing on the account (`order.service.ts`'s `listOrders()`/`getOrder()` were treating `response.data` as the array/object directly). Fixed to unwrap via `ApiEnvelope<Order[]>`/`ApiEnvelope<Order>`. `POST /orders/checkout` has **not** been re-verified since — don't assume it's also drifted without checking.
- **`UserProfile` has no `email` field at all** — not in the type, not in `GET /profile`, not accepted by `PUT /profile` (confirmed against `docs/api.md` and the live type). The Hesabım "Hesab məlumatlarım" screen's design mockup shows an E-mail field; per explicit product decision it's shown as a **disabled, fixed-placeholder field** (`AccountInfoScreen.tsx`, `PLACEHOLDER_EMAIL` constant) purely for visual fidelity — it is never sent to the backend. If the API ever adds real email support, wire that constant up to a real field + validation instead of assuming this is still a stub.
- `react-native-mmkv`/`react-native-nitro-modules` are native modules — after installing/changing their versions, a native rebuild (`cd android && ./gradlew.bat app:installDebug`) is required before `tokenStorage` actually works on-device; type-checking passing does not mean it's linked yet. (This line used to be about `async-storage`, which `tokenStorage.ts` no longer uses — see above.)
- **Verified working end-to-end** (2026-08-17, emulator `android_device`): `signup` and `login` both wired to `LoginScreen`/`RegisterScreen`, tested against the real backend above — signup returned "Qeydiyyat tamamlandı", login returned profile for a real account and stored tokens. `Button` component now supports a `loading` prop (spinner + double-submit guard); form-level API errors surface via a `formError` state + `getApiErrorMessage()` (`src/shared/utils/apiError.ts`), not per-field errors.

## Structure
- **Per-component folder convention (since 2026-08-22)**: most screens/components live as `ComponentName/ComponentName.tsx` + `ComponentName.styles.ts` (the `StyleSheet.create({...})` block, moved out) + `ComponentName.types.ts` (the `type ComponentNameProps = {...}`, if one exists) + `index.ts` (`export { default } from './ComponentName';`, plus re-exports of any named exports like `ProductCard`'s `COLUMNS`/`GRID_GAP`/... or `BasketSummaryBar`'s `SUMMARY_BAR_*`). External imports are unaffected (`@shared/components/ProductCard` still resolves, now via the folder's `index.ts`). Constants that feed directly into the style object (e.g. `CARD_WIDTH`, `HORIZONTAL_PADDING`) live in `.styles.ts`; constants used only in logic/JSX (e.g. `FALLBACK_IMAGE_URL`, debounce/timeout durations) stay inline in the `.tsx` — deliberately **not** further split into a `.constants.ts`, since most are single-use one-liners where separating them from their usage hurts readability rather than helping it (see Working agreements). Applied to every component/screen **except** `src/navigation/HomeStackNavigator.tsx` and `src/navigation/TabBar.tsx`, which are small enough (≤30 lines of styles) that splitting wasn't worth it — left flat on purpose, don't "finish the job" by converting them too.
- `src/screens/auth/` — Welcome, Login, Register (pre-login)
- `src/screens/protected/` — post-login screens: `home/` (HomeScreen, CategoryProductsScreen, ProductDetailSheet, EmptyCategoryState), `basket/` (`BasketScreen.tsx`/`.styles.ts`/`index.ts` sit flat directly in `basket/`, **not** in their own `basket/BasketScreen/` subfolder — that middle folder was redundant since `basket/` only ever holds this one screen, flattened 2026-08-24; this is a deliberate exception to the per-component folder convention below, same reasoning as the `HomeStackNavigator.tsx`/`TabBar.tsx` exception — don't reintroduce a `BasketScreen/` wrapper), `checkout/` (CheckoutScreen, OrderItemsBox, OrderSuccessScreen — redirects to `Profile` → `OrderHistory` on a 3-second countdown after a successful order), `search/` (SearchScreen, debounced), `profile/` (ProfileScreen, AccountInfoScreen, MyListsScreen — favorites grid, OrderHistoryScreen, OrderDetailSheet, AvatarPicker, MenuRow)
- `src/shared/components/` — Button, TextField, Input (see "Password masking" below), InputLabel, Checkbox (used by `LoginScreen`'s "remember me"), AppHeader (top bar with basket icon, used by HomeStackNavigator), ProductCard (grid card used by both `HomeScreen`/`CategoryProductsScreen` and `MyListsScreen`'s favorites grid — exports `COLUMNS`/`GRID_GAP`/`HORIZONTAL_PADDING` layout constants), BasketSummaryBar (floating add-to-basket summary bar, exports its own height/gap constants for screens to reserve list padding), ConfirmModal (used by `ProfileScreen` for logout confirmation and `BasketScreen`'s "Səbəti təmizlə"), ErrorState (message + "Yenidən cəhd et" retry button, used by every screen with a fetch-on-mount), AuthSwitchLink ("Hesabınız var(mı)" links shared by Welcome/Login/Register), ErrorBoundary (wraps the whole app in `App.tsx`, outermost provider — its retry remounts the whole subtree via a `key` bump on a wrapping `Fragment` rather than just clearing the error, since clearing alone re-renders the same crashed state and can loop; **don't revert to a plain `setState({error: null})`** without re-adding that reasoning), icons.tsx (inline SVG icon components — deliberately left flat, not part of the per-component folder convention above since it's a flat bag of small standalone icon functions, not one component)
- **Password masking (`Input.tsx`)**: does **not** rely on native `secureTextEntry` — see Gotchas for why (Android reveals the first typed character for ~2s). Instead always renders `•`-masked text as the controlled `value`, diffs the incoming display text against the previous mask (via common-prefix/common-suffix matching) to recover what the user actually typed/deleted, and forwards the *real* value to the parent's `onChangeText`. `secureTextEntry` is passed as `false` to the underlying `TextInput` always. The eye toggle icon follows "icon shows current state" (closed eye = masked/hidden, open eye = visible) — the opposite convention (icon shows the tap action) was tried first and reverted per explicit user preference.
- `src/shared/utils/validation.ts` — form validators + `applyAzPhonePrefix` (see API layer above)
- `src/shared/api/`, `src/shared/services/`, `src/shared/config/` — API client, per-domain services, env config (see API layer above)
- `src/navigation/RootNavigator.tsx` — root stack: Welcome/Register/Login → Main (tabs) → Basket → Checkout → OrderSuccess, all pushed on the same root stack so they can be reached from any tab. `initialRouteName` is now **token-based** (fixed 2026-08-22, the old permanent `"Main"` bypass is gone): `getAccessToken() ? 'Main' : 'Welcome'`, computed synchronously via MMKV (see API layer above) — no loading screen needed. `BottomTabNavigator` → `HomeStackNavigator` (HomeMain, CategoryProducts) + `ProfileStackNavigator` (ProfileMain, AccountInfo, MyLists, OrderHistory) + TabBar.
- `src/theme/fonts.ts`. `useReload` lives at `src/shared/hooks/useReload.ts` (moved under `shared/` 2026-08-25 — it's cross-screen reusable like the rest of `shared/`, and the old standalone `src/hooks/` held only this one file). It now takes the actual refetch function (`useReload(retry)`) and wires real pull-to-refresh, not a fake timeout — used on `HomeScreen`, `CategoryProductsScreen`, `MyListsScreen`, `OrderHistoryScreen`, `ProfileScreen`, `AccountInfoScreen`; `BasketScreen` wires `RefreshControl` straight to the basket store's own `loading`/`fetchBasket` instead. Removed entirely from `WelcomeScreen`/`LoginScreen`/`RegisterScreen` — they have no server data to refetch.
- `types/` — **project root**, not under `src/`. `svg.d.ts` (ambient `*.svg` module decl), `navigation.ts` (RootStackParamList, ProtectedTabParamList, HomeStackParamList — nested navigators are typed with `NavigatorScreenParams<...>` so `navigation.navigate('Main', { screen: 'Home', params: { screen: 'HomeMain' } })` type-checks), `api.ts` (backend response/domain types, mirrors `docs/api.md`). This root-level `types/` is for types genuinely **shared across multiple unrelated files**; a single component's own props type belongs in its own folder's `ComponentName.types.ts` instead (see per-component folder convention above) — don't centralize component-local prop types here.

## Gotchas / decisions already made (don't redo the investigation)
- **React Native 0.83.0 has a core Android regression that breaks all `FormData`/multipart uploads** (axios and fetch both affected) — every request fails immediately with a generic `AxiosError: Network Error` / `ERR_NETWORK`, no response, no useful server-side signal (introduced by an RN core PR, tracked at facebook/react-native#54881). Confirmed via raw error logging while debugging the profile-avatar upload feature: `error.response` was `undefined` (never reached the server), same request worked fine once RN was bumped. **Fixed by upgrading `react-native` (+ matching `@react-native/*` packages) from `0.83.0` to `0.83.10`** — multiple people on the GitHub issue confirm `0.83.1`+ resolves it. If any *other* FormData/file-upload endpoint starts throwing bare "Network Error" with no response on Android, re-check the installed `react-native` patch version before assuming it's an app bug.
- **`@gorhom/bottom-sheet` v5 silently doesn't work with this project's `react-native-reanimated` v4** — `BottomSheetModal.present()` runs with no JS error, `useEffect`/console logging confirms it's called with the correct ref and layout, but the sheet never becomes visible (tried both `enableDynamicSizing` and explicit `snapPoints`). Reanimated v4's worklets architecture is very new; downgrading reanimated to v3 to match was also tried and does **not** work — v3's Android Java bridge code (`ReanimatedModule.java`) doesn't compile against RN 0.83's New Architecture APIs (`UIManagerModuleListener` etc. no longer exist), so v3 is a dead end on this RN version too. Resolution: dropped `@gorhom/bottom-sheet` entirely, kept `react-native-gesture-handler` (which *is* reanimated-independent and works fine standalone), and built a custom bottom sheet (`src/shared/components/BottomSheet.tsx`) with core RN `Animated` + `PanGestureHandler`. Don't re-attempt `@gorhom/bottom-sheet` on this project without confirming upstream has caught up to reanimated v4.
  - Building that custom sheet surfaced two more gesture-handler-specific traps, both already fixed in `BottomSheet.tsx` — don't redo the debugging:
    - `PanGestureHandler`'s `onGestureEvent` bound via `Animated.event` applies the raw (possibly negative) `translationY` with no clamping — dragging down then back up past the start point before releasing pushes the sheet **above** its resting position. Fix: drive the value through a plain JS callback (`translateY.setValue(Math.max(0, translationY))`), not `Animated.event`, so it can be clamped every frame.
    - `GestureHandlerRootView` only needs to exist **once**, at the app root (`App.tsx`). We initially also nested one inside `BottomSheet.tsx`'s `Modal` (seemed necessary since `Modal` renders in a separate native Android window that the root-level one doesn't cover) — but the `TouchableOpacity` overlay/sheet wrappers inside that inner `GestureHandlerRootView` must stay **core RN `TouchableOpacity`**, not gesture-handler's re-exported one. Swapping them to gesture-handler's version (attempted while chasing an unrelated scroll-lag bug) silently broke the `flex:1`/`justifyContent:'flex-end'` layout — the sheet rendered pinned to the top of the screen instead of the bottom, invisible (white-on-white) and intercepting all touches underneath it app-wide. Only gesture-handler's `ScrollView` (used for the order-detail item list) needed swapping to fix the actual scroll-lag issue; the outer `TouchableOpacity`s did not.
- **`npx react-native run-android` fails on this machine**: Node ≥20.11/18.19.1 (CVE-2024-27980 fix) blocks direct `.bat` spawning, breaking the RN CLI's gradlew invocation. Workaround: build directly with `cd android && ./gradlew.bat app:installDebug` (PowerShell, not Git Bash), then `adb shell am start -n com.tiktak/.MainActivity`.
- Release APKs: `npm run apk` runs `scripts/build-apk.js`, which invokes `gradlew.bat assembleRelease` and copies the output to a top-level `/apk/tiktak-<timestamp>.apk` (easier to find than digging through `android/app/build/outputs`). It calls `gradlew.bat` via its **full resolved path**, not a bare/relative name — with Node 24 + `shell:true`, cmd.exe's implicit cwd-search for `gradlew.bat` wasn't finding it even with `cwd` set correctly. Same underlying Node/`.bat`-spawning issue as the `run-android` workaround above.
- Physical Android device connects over WiFi debugging: `adb pair <ip:port> <code>` → `adb connect <ip:port>` → `adb reverse tcp:8081 tcp:8081` (needed for Metro; reverse mapping drops if device reconnects/switches transport, must redo it if `Unable to load script` appears). Some devices (Xiaomi/Redmi) block `adb shell input tap/keyevent` even with USB debugging unless "USB debugging (Security settings)" is separately enabled — screenshots still work, just not input injection.
- **On the `xeyya`-user Windows machine (a different/fresher machine than the `Mr Frontend`-user one the rest of this doc's Gradle/SSL gotchas were written on, and with no emulator/AVD set up — physical device over USB only), the Gradle daemon JVM (Temurin 17, `C:\Users\xeyya\AppData\Local\Android\Sdk`) segfaulted mid-build twice** (`EXCEPTION_ACCESS_VIOLATION` inside JIT-compiled code — once in C2-compiled `ASM ClassReader::readMethod`, once in C2-compiled `ConcurrentHashMap.transfer`, both at different points in the task graph, on an AMD Ryzen 7735HS) — looked JIT-compiler-bug-shaped, not a project code issue. **Fixed** in `android/gradle.properties`'s `org.gradle.jvmargs` by adding `-XX:TieredStopAtLevel=1` (disables the C2 JIT, forces C1-only) — but C1-only burns through the default JIT code cache faster, which then hit `VirtualMachineError: Out of space in CodeCache for method handle intrinsic` during D8 dexing, so also added `-XX:ReservedCodeCacheSize=512m` alongside it. Both flags are already in `gradle.properties`; if a *build* (not app) crash recurs on this machine with a similar `hs_err_pid*.log` JIT-frame signature, re-check these flags are still present before re-diagnosing from scratch.
- Android 12+ system splash screen icon is **always circle-masked** by the OS — can't be styled square. Fixed by setting `android:windowSplashScreenAnimatedIcon` to a transparent 1dp drawable in `values-v31/styles.xml` (API 31+ override of `BootTheme`) so no visible shape flashes before our custom bootsplash view takes over.
- Android edge-to-edge (targetSdk 35+) forces a translucent scrim over the nav bar; plain `android:navigationBarColor` isn't enough — also need `android:enforceNavigationBarContrast`/`enforceStatusBarContrast` set to `false` in `AppTheme`.
- Keyboard handling: uses `KeyboardAwareScrollView` from `react-native-keyboard-controller` (NOT `KeyboardAvoidingView` + manual `behavior` — Android `adjustResize` + JS-level height/padding double-adjust and desync after keyboard close, leaving a residual gap). The library's `ScrollViewWithBottomPadding` wrapper hardcodes `flexGrow:1` internally — a footer/button placed as a sibling outside the ScrollView will always get pushed to the screen bottom regardless of content length; keep the submit button **inside** the ScrollView's content instead if it should sit right after the form fields. Manual `onFocus` → `scrollToEnd()` is used to guarantee the button is reachable when focusing early fields too; use `progress.value` (`useReanimatedKeyboardAnimation`) to pick 0ms delay if keyboard's already open vs ~300ms if it still needs to animate open, otherwise the scroll races the keyboard/ghost-padding animation and jumps.
- `react-native-bootsplash` generate CLI warns/fails past certain logo `--logo-width` sizes: >134dp shows a cropping warning, >192dp refuses to generate. Keep it under 134 for the actual Android system splash icon; a taller/wider custom logo (e.g. logo + wordmark stacked) can still be used for the in-app custom splash view as long as its *effective* dp width stays in range.
- **Gradle fails to download any brand-new dependency with an SSL handshake error** (`certificate_unknown ... PKIX path building failed`), even though `curl`/browsers work fine: this machine's **Avast Antivirus does TLS-inspection (MITM) on all HTTPS**, re-signing certs with its own root CA (`Avast Web/Mail Shield Root`). That root is trusted by Windows (so curl/browsers are fine) but **not** by the standalone Eclipse Adoptium JDK Gradle uses — so any artifact not already cached in `~/.gradle` fails to resolve, from any host (`dl.google.com`, `repo.maven.apache.org`). This is why adding `@react-native-async-storage/async-storage@3.x`/`2.x` failed (their build needs KSP/Room artifacts never fetched before) while everything already-cached kept working. **Fix already applied on this machine** — don't redo it, don't ask the user for admin rights: exported the Avast root cert from `Cert:\LocalMachine\Root` (PowerShell), imported it into a **user-writable copy** of cacerts at `C:\Users\Mr Frontend\.gradle\cacerts-with-avast.jks` (via `keytool -importcert`, avoids needing admin rights to touch the protected JDK cacerts under `Program Files`), and pointed Gradle at it globally via `C:\Users\Mr Frontend\.gradle\gradle.properties`:
  ```
  systemProp.javax.net.ssl.trustStore=C\:\\Users\\Mr Frontend\\.gradle\\cacerts-with-avast.jks
  systemProp.javax.net.ssl.trustStorePassword=changeit
  ```
  If a *new* machine/user hits this same SSL error, redo this exact recipe (`Get-ChildItem Cert:\LocalMachine\Root | Where Subject -match "Avast"` → export → `keytool -importcert` into a copy of cacerts → `systemProp.javax.net.ssl.trustStore` in the user's global `~/.gradle/gradle.properties`) rather than downgrading packages to dodge it — downgrading (as done for async-storage) is a workaround for *that specific package*, not a fix for the underlying machine issue.
- Metro's file watcher (`FallbackWatcher`) crashes the whole Metro process with an uncaught `ENOENT` if a directory it's watching gets deleted mid-scan — this reliably happens from Gradle's transient CMake temp dirs (`.cxx/.../CMakeTmp/...`) and from npm's temp package-swap dirs (`node_modules/@scope/.pkg-RANDOM`) during `npm install`. Symptom: app hangs forever on the bootsplash screen with no error on-device because Metro silently died. Fix: just restart Metro (`npx react-native start`, add `--reset-cache` if a resolver error mentions a file that demonstrably exists on disk — Metro's haste map can go stale across rapid `npm install` swaps).
- **A `position:'absolute'` footer sibling can make a same-parent box "overlap" it even though `marginBottom`/`overflow:hidden`/`borderRadius` all look correct** — this cost a long back-and-forth in `CheckoutScreen`/`BasketScreen`. Root cause: `marginBottom` on a normal-flow sibling only affects the *next flow sibling's* position; an absolutely-positioned element (e.g. a footer pinned with `left/right/bottom:0`) is removed from flow and ignores that margin entirely, so a fixed/flex-sized box can visually extend *underneath* it. Symptom looked exactly like an Android "ScrollView won't clip to borderRadius" rendering bug (only top corners rounded, bottom corners look square) — multiple attempts at fixing the *radius* (adding `overflow:hidden`/`borderRadius` directly on the `ScrollView`, decoupling the rounded background into its own absolutely-positioned child `View`) didn't help because the real problem was the opaque footer painting over the bottom of the box, not a clipping failure. Fix: keep footer elements in normal flow (no `position:'absolute'`) so the box physically cannot render behind it, rather than trying to reserve space for an absolute footer via margin/padding math.
- **Locking a box's height via "flex:1 on first layout, then read `onLayout` and switch to a fixed `height`" must also clear `flex` on that later style, or the earlier `flex:1` keeps winning** — `flex:1` sets `flexBasis:0%`, which takes priority over an explicit `height` in Yoga's main-axis sizing, so leaving `flex:1` active alongside a `height` override silently ignores the fixed height and the box keeps flex-growing. This surfaced as the box growing 2-3px whenever Android's keyboard closed (its `adjustResize` window resize gives flex-grow elements more room) — e.g. right when a submit button is tapped from a focused text field. Needed a real "flex:0"-style override class, not just adding a `height` key.
- **Adding a New Architecture native module with its own CMake codegen (e.g. `react-native-gesture-handler`) can fail Windows builds with `ninja: error: ... Filename longer than 260 characters`** — the autolinked lib's intermediate object path (`android/app/.cxx/Debug/<hash>/<abi>/<lib>_codegen_autolinked_build/.../<LongNodeModulesPath>...cpp.o`) combines with this project's already-long absolute path (`D:\Praqramlasdirma\Homeworks\Tiktak\...`) and exceeds Windows' MAX_PATH. Fixed **without needing admin rights / Windows long-path registry changes** by redirecting CMake's staging dir to a short drive-root path in `android/app/build.gradle`:
  ```groovy
  android {
    externalNativeBuild {
      cmake { buildStagingDirectory "C:/rnbuild/tiktak-cxx" }
    }
  }
  ```
  If a *new* native module addition hits this same "Filename longer than 260 characters" error, this block is already in place — just confirm `C:/rnbuild/tiktak-cxx` is writable, don't re-diagnose from scratch.
- `adb shell input tap <x> <y>` needs **actual device pixel coordinates** (this emulator is 1080×2400), not the coordinates read off a downscaled screenshot preview (often shown at 900×2000) — multiply the preview coordinates by the scale factor (e.g. ×1.2) or taps land on the wrong element. Different screens can also have the primary button at different y-offsets (e.g. Login's button sits higher than Register's since it has one fewer field) — don't reuse a tap coordinate across screens without rechecking the screenshot.
- **Android's native `TextInput secureTextEntry` visibly shows the first typed character in plaintext for ~2 seconds before masking it** — an OS-level "peek" animation (not a JS timing bug), most noticeable on the very first character since there's usually a pause before the next keystroke; later characters mask fast enough that it's not noticed. Confirmed by testing: happens even with a fully controlled `value`/`onChangeText`, regardless of `autoCorrect`/`autoComplete`/`importantForAutofill` props (tried disabling all of them first, didn't help). **Fixed by not using native `secureTextEntry` masking at all** — see `Input.tsx`'s manual masking, described under Structure above. If a future RN/Android version fixes this upstream, the manual masking can be reverted, but don't assume that's already true without testing on-device first (an emulator alone isn't representative — this project has repeatedly found emulator-only testing to miss real-device-only bugs).
- **`react-native-mmkv@4` throws `Cannot read property 'prototype' of undefined` if you write `new MMKV(config)`** — v4 rewrote the library on Nitro Modules; `MMKV` is now only a TypeScript type, the actual runtime constructor is the `createMMKV(config)` function. Also requires `react-native-nitro-modules` installed as a real dependency (not just implied by `react-native-mmkv`'s peerDependency) — `npm install react-native-mmkv` alone leaves the Gradle build unable to find the `:react-native-nitro-modules` project. Both are already fixed in this project's `tokenStorage.ts` and `package.json` — if adding a *second* MMKV instance elsewhere, use `createMMKV(...)`, not `new MMKV(...)`.
- **Metro's haste map can go stale after many files are created/deleted rapidly by tooling (not just `npm install`, see the existing FallbackWatcher entry above)** — during the 2026-08-22 folder-structure refactor (creating ~30 new files, deleting ~30 old ones in quick succession), Metro started throwing `UnableToResolveError: Unable to resolve module ./ComponentName.styles` for files that demonstrably existed on disk and were correctly imported. A plain Metro restart did **not** fix it; needed a full `npm start -- --reset-cache`. If a resolver error names a file that you can confirm exists with the right content, suspect a stale haste map before suspecting the import path. **Recurred 2026-08-25** after moving `src/hooks/useReload.ts` → `src/shared/hooks/useReload.ts`: a long-running Metro instance kept resolving the old deleted path (`Unable to resolve module ../../../../hooks/useReload`) and the app hung forever on the "Loading from localhost:8081..." splash with no error surfaced to logcat — looked exactly like a JS-thread hang, not a resolver error, until Metro's own terminal log was checked directly. Same fix: kill Metro, restart with `--reset-cache`.
- **`OrderSuccessScreen`'s post-order redirect used `navigation.navigate('Main', {...})`, which should pop back to the existing `Main` route and discard everything pushed on top of it (`Basket`/`Checkout`/`OrderSuccess`) — but didn't reliably do so.** Symptom (found by the user, confirmed fixed on-device 2026-08-25): place an order, let the 3-second countdown redirect to Sifarişlərim (or tap "Əsas səhifəyə qayıt"), navigate around elsewhere, then press the hardware back button repeatedly — you could still land back on the "Sifarişiniz uğurla göndərildi" screen, which should be a one-shot/transient screen with no way back into it. **Fixed** by switching both exit paths in `OrderSuccessScreen.tsx` (`goToOrderHistory` and the button's `onPress`) from `navigate` to `navigation.reset({ index: 0, routes: [{ name: 'Main', params: {...} }] })`, which unconditionally throws away the whole root stack instead of relying on `navigate`'s "pop to existing screen" behavior. If a similar "screen reachable via back that shouldn't be" bug shows up elsewhere (any post-transaction success screen), reach for `reset` from the start rather than `navigate` — don't assume `navigate`'s implicit-pop behavior is reliable when nested-navigator params are involved.
